# Phase 12 — UI Design Contract

> Visual and interaction contract for Spotify account linking, Library browsing, playlist detail, and export on Next.js web and Flutter Android. Generated by gsd-ui-researcher; verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | Existing manual Harmonix systems: Tailwind/custom React components on web; Material 3 on Flutter |
| Preset | Not applicable; do not initialize shadcn during this phase |
| Component library | Existing `Button`, `Input`, Radix primitives, and Lucide on web; Material 3 widgets on Flutter |
| Icon library | Lucide React on web; Material Symbols on Flutter; official Spotify logo asset for provider attribution only |
| Font | Inter on Flutter; Inter or the existing web sans-serif stack on Next.js, preserving identical role sizes and weights |
| Visual source | Phase 10 light/green system plus the Phase 12 Library designer reference |

This phase extends the current component systems rather than introducing a third design system. New web surfaces must use the light Harmonix treatment by default and remain compatible with the existing `.dark` theme. Flutter uses `HarmonixColors.of(context)` and existing theme roles; do not hard-code theme-dependent text or surfaces in widgets.

Spotify branding is provider attribution, not the Harmonix design system. Use the official Spotify mark without recoloring, distortion, masking, or placing it inside a generic music icon. Do not use Spotify green for Harmonix controls, success messages, progress bars, or decorative borders. Every surface displaying Spotify metadata must expose an API-provided `Open in Spotify` link where the state permits it. Per the current official design guidance checked 2026-07-19, one Spotify content set displays at most 20 items and ends with an API-provided onward link to Spotify. Harmonix does not invent client pagination to display additional Spotify items; continuation occurs in Spotify.

## Spacing Scale

Declared values (multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps, provider badge internal gap |
| sm | 8px | Compact control gaps, metadata rows |
| md | 16px | Card padding, row gaps, modal padding |
| lg | 24px | Section spacing, mobile horizontal page padding |
| xl | 32px | Desktop card-grid gaps, detail header spacing |
| 2xl | 48px | Empty-state and report section separation |
| 3xl | 64px | Desktop page-level breathing room |

Exceptions:
- Interactive targets are at least 44×44px on touch and 40px high on pointer-first web.
- Spotify artwork is 48px in compact rows, 64px in playlist cards, and 160px maximum in the detail hero.
- Progress bars may be 8px high.
- Web content max width is 1120px for Library and 800px for Settings/report; Flutter remains one fluid column.

## Typography

Phase 12 additions use exactly four sizes and two weights:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label / metadata | 14px | 400 | 1.4 |
| Body / control | 16px | 400 | 1.5 |
| Section heading | 22px | 700 | 1.2 |
| Page / detail display | 32px | 700 | 1.2 |

Rules:
- Provider badges use 14px/700; button labels use 16px/700.
- Uppercase section labels are allowed only for `HARMONIX PLAYLISTS`, `SPOTIFY PLAYLISTS`, and `RECENT DISCOVERIES`; add letter spacing but retain 14px.
- Playlist and track names use sentence case. Do not transform Spotify-supplied names.
- Long names wrap to two lines in detail headers and truncate to one line with ellipsis in cards/rows; the full value remains available to assistive technology and pointer hover.

## Information Architecture

### Navigation

- Preserve the Flutter tab order: Discover · Library · Learn · Settings. Learn remains the ordinary default tab.
- A successful Spotify OAuth completion overrides the ordinary default once: open/select Library, announce success, and begin playlist synchronization.
- A canceled or failed OAuth flow returns to Settings with the Spotify card in disconnected/error state.
- Web uses the existing Harmonix app header and responsive page navigation. Settings and Library are distinct destinations; the primary connection action exists only in Settings.
- Provider-aware route identity must include both provider and stable provider ID. A Spotify ID must never be interpreted as a Harmonix playlist ID.

### Settings order

1. Page heading.
2. Existing user profile.
3. Spotify connection card.
4. Appearance.
5. Stats.
6. Achievements.
7. Log out.

The connection card must be visible without scrolling on a typical Android handset after the profile block. On web, place it in the first content column under the account/profile block, not in a sidebar or footer.

### Library order

1. Page header and existing Harmonix create action.
2. `HARMONIX PLAYLISTS`.
3. `SPOTIFY PLAYLISTS`.
4. `RECENT DISCOVERIES`.

The provider groups share one playlist-first region but remain visually separated by headings. Do not interleave provider cards. If a provider group is unavailable, keep the other group functional and preserve its position.

## Responsive Layout Contract

| Viewport | Contract |
|----------|----------|
| Flutter / web under 640px | One column; 20–24px side padding; full-width cards; sticky/native bottom navigation where already present; modal actions stack only when labels would wrap |
| Web 640–1023px | One or two playlist-card columns based on a 280px minimum card width; Settings remains one readable column; report uses stacked summary and tables |
| Web 1024px and above | Centered 1120px Library; separate provider sections each use a three-column card grid when space permits; Recent Discoveries and export report max at 800px for scanning |

Do not copy the designer reference’s fixed mobile dimensions. Preserve its composition, hierarchy, compact bordered cards, and song-row rhythm. Reflow based on available width; never horizontally scroll the page.

## Component Inventory

### Spotify connection card

An outlined secondary-surface card directly below the profile:
- Leading official Spotify mark at 32px.
- Title/status and one line of explanatory copy.
- Primary action aligned trailing on wide web and below copy on narrow/mobile.
- Optional secondary `Disconnect Spotify` text action only in connected state.
- Account display name may appear as muted metadata when returned by the backend; never show email, tokens, scopes, or internal Spotify IDs.
- Status is expressed by text and icon, never color alone.

### Provider badge

- Compact 14px/700 label with icon and text: `Harmonix` or `Spotify`.
- Harmonix badge uses the Harmonix accent outline.
- Spotify badge uses official attribution and neutral surface; do not create an imitation Spotify logo.
- Cards and detail headers both carry the badge.

### Playlist card

- Entire card is one navigation target; nested destructive/export controls must be separate and must not trigger navigation.
- Shows 64px artwork or provider-specific neutral placeholder, playlist name, `{n} tracks/songs`, provider badge, and chevron.
- Missing artwork falls back to a bordered music-note tile; do not fetch arbitrary fallback images.
- Spotify card destinations:
  - owned/collaborative and detail-readable → in-app detail;
  - followed/restricted → restricted in-app detail with `Open in Spotify`.
- Harmonix cards retain existing create/delete behavior and stable local navigation.
- The Spotify playlist shelf displays at most 20 cards. After the twentieth card, render `Open more playlists in Spotify` using an API-provided current-user Spotify URL when available; if the API contract does not provide a safe onward URL, display only the first 20 and the policy-review gate remains blocked rather than constructing one.

### Recent Discoveries row

- Remains below both playlist groups.
- Shows the learned word, translation, and associated artist/title.
- Preview control, if present, invokes only the existing validated Deezer 30-second preview path.
- Never display a Spotify play control or Spotify playback progress.

### Playlist detail

- Provider badge, artwork, playlist name, owner/visibility metadata when available, count, and primary action area.
- Spotify detail always includes `Open in Spotify` using the API-provided URL.
- Track rows show track number, title, artists, optional duration, and availability state.
- Null, local, unavailable, or market-restricted items render a disabled row with `Unavailable on Spotify`; they are never silently omitted if the backend reports them.
- Spotify detail has no remove/edit control in Phase 12.
- Harmonix detail retains current song navigation/removal and adds `Export to Spotify` when connected.
- A readable Spotify detail displays at most 20 item rows and then an API-provided `Open in Spotify` continuation action for the playlist. Do not add local next/previous pagination or infinite loading for Spotify rows unless a later official contract and policy review explicitly permit it.

### Export initiation

- `Export to Spotify` appears on an owned Harmonix playlist detail only when it has at least one song and Spotify is connected.
- Selecting it opens a confirmation sheet/dialog showing source playlist, song count, destination `Private Spotify playlist`, and explanatory text: `Harmonix will match tracks before creating anything in Spotify.`
- Primary action: `Start export`; secondary: `Cancel export`.
- If disconnected or expired, replace export with `Reconnect Spotify`, routing to the Settings card.

### Export progress

- Use a determinate progress bar when total source count is known.
- Stages: `Matching {current} of {total} tracks` then `Creating playlist in Spotify`.
- Disable duplicate submission and navigation-triggering export actions while active.
- Closing a mobile sheet must not imply cancellation if the server job continues; returning to the detail restores status.
- Export identity is not owned by the dialog/sheet or detail widget. On every web or Android detail load, query the authenticated latest export for that owned source playlist; when a job ID is known, restore it through the authenticated by-ID status route. A closed sheet, route recreation, Android process recreation, or web refresh therefore restores backend-confirmed progress/report.
- Do not use fake percentage animation. Honor reduced-motion preferences.

### Match report

- Summary panel: `Matched {matched} of {total}`, `Unmatched {unmatched}`, and export destination.
- Success state includes `Open in Spotify` and `Finish export`.
- Matched rows show source title/artist and matched Spotify title/artist; cached and newly searched matches look the same to users.
- Unmatched rows are listed under `Needs review` with a concise reason such as `No confident match` or `Track unavailable in your market`.
- Partial provider mutation failure uses `Exported {exported} of {matched} matched tracks` and keeps the factual report; never claim full success.
- No manual match override is in scope.

### Confirmation and feedback surfaces

- Web uses accessible dialogs with trapped focus, Escape/cancel behavior, initial focus on the non-destructive action, and focus restoration.
- Flutter uses `AlertDialog` or modal bottom sheet according to current platform pattern.
- Success can use a brief toast/snackbar, but reconnect, rate-limit, restricted, and export report states must remain visible in content.

## Connection State Machine

| State | Visual contract | Enabled actions |
|-------|-----------------|-----------------|
| Connect / disconnected | Spotify mark, `Connect Spotify`, concise benefit copy | Connect |
| Connecting | Inline spinner plus `Connecting to Spotify…`; card remains present | No duplicate connect; allow browser cancellation only |
| Connected | Success icon, `Spotify connected`, optional account name, last-sync metadata | View Library; Disconnect Spotify |
| Reconnect required | Warning icon, expired-session copy | Reconnect; Disconnect Spotify cleanup |
| Disconnecting | Inline spinner plus `Disconnecting…` | No actions |
| Disconnected after action | Neutral confirmation `Spotify disconnected`; stale provider data removed from view immediately | Connect |
| Provider/error | Error icon and safe recovery copy | Retry sync or Reconnect depending on backend error code |

Connect opens the Spotify authorization surface in the system browser/new browser context. Before leaving, preserve the Settings state. Never place Harmonix credentials, Spotify tokens, authorization codes, or state in visible UI.

On successful callback:
1. Show a transient `Spotify connected` announcement.
2. Navigate directly to Library.
3. Render Harmonix content immediately.
4. Render Spotify playlist skeletons while synchronization runs.
5. Replace skeletons with cards, empty state, or actionable provider error.

## Library and Provider States

| State | Required behavior |
|-------|-------------------|
| Initial loading | Preserve headings; show three card skeletons in each unresolved playlist group and row skeletons for Recent Discoveries; do not block the whole page with one spinner |
| Harmonix loaded, Spotify loading | Render Harmonix and Recent Discoveries normally; skeleton only the Spotify section |
| Populated | Provider-separated cards first, Recent Discoveries after; counts use correct singular/plural |
| Fully empty | Render the documented empty Library copy and retain Harmonix create action; no Connect button in Library |
| Spotify connected but empty | Show Spotify empty-state copy and `Refresh playlists`; do not suggest reconnect |
| Spotify disconnected | Compact inline notice: `Connect Spotify from Settings to see your playlists.` Link label `Open Settings`; never a primary Connect button |
| Followed/restricted playlist | Keep clearly marked card if returned; tapping opens restricted in-app detail with explanation and `Open in Spotify` |
| Partial provider data | Render usable cards; missing artwork uses placeholder, unknown count uses `Track count unavailable`, and a non-blocking notice offers `Refresh playlists` |
| Provider error | Spotify section contains safe error copy and `Retry sync`; Harmonix content remains interactive |
| Offline | Show persistent offline banner in the Spotify section; retain last locally permissible non-stale Harmonix content; disable sync/export |
| Rate limited | Keep existing content, show countdown/retry time, disable manual refresh until eligible, and do not spin continuously |
| Expired session | Remove/obscure stale Spotify personal data and show `Reconnect Spotify` link to Settings |

Pull-to-refresh on Flutter and explicit `Refresh playlists` on web request all Library sources, but provider failures remain isolated. Never clear successfully loaded Harmonix content because Spotify refresh fails.

## Export States

| State | Required behavior |
|-------|-------------------|
| Not eligible | Hide export for Spotify source playlists; disable with explanatory text for empty Harmonix playlists |
| Ready | `Export to Spotify` available on Harmonix detail |
| Matching | Determinate progress and current/total text; submission locked |
| Zero matches | Do not create a Spotify playlist; show unmatched report and zero-match copy |
| Match complete | Begin mutation only after accepted matches exist |
| Creating | Show creation stage; do not allow a second export |
| Success | Show report, destination name, and `Open in Spotify` |
| Partial success | State exact exported/matched/total counts; preserve unmatched and failed rows; `Open in Spotify` only if a destination exists |
| Offline | Prevent initiation; retain any completed report already returned |
| Rate limited | Preserve progress/report, show retry timing, and resume only through backend-confirmed state |
| Expired session | Stop before further mutation and route user to reconnect; preserve non-sensitive local match report |
| Provider error before creation | State that no playlist was created |
| Provider error after creation | State that the destination may be incomplete and provide `Open in Spotify` when safe |

## Interaction Contract

- One tap/click performs one action. All network mutations become disabled immediately and remain disabled until the backend resolves.
- Flutter supports pull-to-refresh for Settings status, Library, and detail. Web uses visible Refresh controls where recovery is needed.
- Keyboard: all controls are reachable in logical DOM order; Enter/Space activate; card navigation is not implemented with nested interactive elements.
- Focus: use the Harmonix accent focus ring with at least 2px visible width. After route load, focus/announce the page heading; after OAuth success, announce `Spotify connected. Loading your playlists.`
- External links include an external-link icon and accessible name, for example `Open “Road Trip” in Spotify`.
- Destructive disconnect always requires confirmation. It deletes the connection immediately after confirmation and optimistically removes Spotify content only once the backend acknowledges deletion.
- Refresh, retry, and reconnect are distinct: refresh repeats data loading, retry repeats a transient request, reconnect starts OAuth after invalid/expired authorization.
- Back navigation from Spotify detail returns to the prior Library scroll position where platform routing permits.

## Accessibility and Content Robustness

- Meet WCAG 2.2 AA: 4.5:1 normal text contrast, 3:1 large text/control boundaries, visible focus, semantic headings, and no color-only states.
- Spinners and progress bars have text labels; progress exposes current and total values.
- Provider logos have accessible provider names; decorative duplicate marks are hidden from assistive technology.
- Skeletons are not individually announced. Mark the containing region busy and announce completion once.
- Error notices use alert semantics only when newly raised; persistent state copy uses ordinary status semantics to avoid repeated announcements.
- Support text scaling to 200% without clipped controls. At large text, card actions stack and metadata wraps.
- Respect reduced motion. Use no pulsing provider logos, auto-scrolling carousels, or decorative export animation.
- Do not rely on swipe-only or hover-only actions.
- Spotify-supplied text is untrusted display data: render as plain text, never HTML; normalize only for layout, not for display.
